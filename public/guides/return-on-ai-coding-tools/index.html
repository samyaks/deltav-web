How to measure the return on AI coding tools

Cursor, GitHub Copilot, and Claude Code are now a real line in the engineering budget. Here is a method for showing what that line buys.

The short answer

To measure the return on AI coding tools, add up the full cost per engineer, measure how many paid seats are actively used, pick one delivery outcome such as merged pull requests, and track cost per outcome by team over time. Then act on what you find: reclaim idle seats and move heavy users to the plan that fits them.

Why this is hard

The cost side arrives in pieces. Seat licenses are on one invoice, usage-based overages on another, and API keys that engineers use for agents sit in a third place. The value side is worse: most teams fall back on surveys asking engineers how much time they saved, and finance does not treat a survey as evidence.

Step 1. Get the full cost per engineer

Count everything, not only the seat price. That means seat licenses, usage-based charges above the plan's included amount, and model API spend from coding agents that run on your own keys. Most vendors expose this through admin reporting. Cursor's Admin API returns usage and spend per team member, GitHub provides Copilot usage metrics for organizations, and Anthropic and OpenAI both offer usage and cost reporting to administrators.

Step 2. Measure active use per seat

A seat nobody opens returns nothing. For each tool, find the share of paid seats with meaningful activity in the last 30 days. This is the fastest win in the whole exercise, because idle seats can be reclaimed the same week with no debate about productivity.

Step 3. Pick one outcome metric

Choose a delivery outcome your team already trusts: merged pull requests, cycle time from first commit to merge, or tickets closed. Avoid lines of code and suggestion acceptance rate. Both measure activity inside the tool, not work delivered.

Step 4. Calculate cost per outcome and compare

Divide AI cost by the outcome, per team, per month. The number on its own means little. The comparison is what matters: the same team before and after adoption, or similar teams with heavy and light use. Be honest about the limits. This shows association, not proof of cause, so state that plainly when you present it.

Step 5. Act on it

Measurement only pays off when it changes something. The usual actions are reclaiming unused seats, moving light users to a cheaper plan, setting spend limits for users whose usage-based charges run away, and putting more budget behind the teams where cost per outcome is falling.

Common mistakes

  • Counting seat price only and missing usage-based charges.
  • Reporting time saved from a survey as if it were measured.
  • Averaging across the whole company, which hides the teams where the tools pay off and the ones where they do not.
  • Measuring once. The return on these tools moves every time pricing or models change.
